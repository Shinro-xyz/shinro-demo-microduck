shinro-demo-microduck CAKE trajectory swap — tracking-error finding (2026-10-14; ROOT CAUSE CONFIRMED + mechanism). Client mirrors capsule paths via trajectory.py for per-module cross-track error (trace.csv `cross_track`). (1) Vertical steps at swap times = metric artifact. (2) The post-swap RAMP is real divergence. ROOT CAUSE (confirmed with a runtime DIAG on branch `adil/fix/epoch-guard-binding-port` of shinro-cake): the epoch guard NEVER carries a snapshot, so the policy falls back to its BIND-TIME provider table. DIAG proof at the swap: `entries=411 snapshots_filled=0 port_publications=3 refused_port_publications=0`, and at adopt every consumer's port cell is registered (`cell != 0`) AND populated (`cell_value != 0`). MECHANISM: `cake-epoch/src/imports.rs::cake_owned_thread_register` line ~325 caches the port ONCE at registration — `slot.port.store(domain.port_of(instance), Release)` — and `cake_epoch_enter` reads `domain.slots[i].port` (a per-thread slot), NOT the `ports` table `publish_port` writes. In the production path, `activation.rs` runs the module's `activate()` (spawns the owned thread → `owned_thread_register`) BEFORE `plan_entry.rs`→`LiveGraph::adopt`→`register_port`→`publish_port`, so `port_of(instance)==0` at registration → `slot.port=0` forever → every guard carries 0. Same for an incoming generation: `composition.rs::bring_up_incoming` calls `register_port` AFTER `activate`. `activation.rs:841` does write the committed snapshot into the CELL (step 9), but registering the cell ADDRESS with the domain happens too late. Consequence: the module reads its bind-time `g_cmd_table` (initial provider); before a swap it tracks, after the swap the retired provider's thread is quiesced so its table freezes → the robot walks off. Live swap has therefore never routed through the guard. FIX OPTIONS: (A) publish the port cell to the domain before the module's activate() (activation step 8/9) + make register_port tolerate AlreadyPublished; (B) give `Slot` the instance it registered and have `publish_port` backfill already-registered slots (order-independent, cake-epoch-local, also fixes the incoming generation) — recommended. EXONERATED bit-exactly: module cmd == Python PurePursuitTracker; Cake policy == bare .so <=2e-16 (demo kernel was STALE; rebuilt hash 6dbc98c7 == the Cake module's graph). RULED OUT: lag/aliasing (bare converges for fixed/growing 0->40-tick/jitter/random-walk lag), path sampling 400 vs 512, entry pose/heading, sim reset, adopt-missing-publish_initial (refuted: publish_initial is hosted-only by design). KEY SECOND FINDING: atomic ≠ bumpless. In the FUSED design the policy owns the sim socket, so a policy swap tears down the plant link: the demo client logs "the Cake module connection went away; stopping" and ends at the swap (steps=110/~2.2s of a 6s run). So the swap is atomic (COMPLETED, session unchanged, epoch advanced, new plan committed) but the walk STOPS — it is not even a pause, the single-accept client exits. That is the empirical case for the bridge split (stable clock/socket owner + policy as a swappable leaf). The honour shutdown drain also reports deadline_exhausted=1 (new policy generation didn't quiesce in the budget at kill). Refuse phase abort touches nothing, so the walk continues there. <!-- created=2026-10-15, last=2026-10-15 -->
